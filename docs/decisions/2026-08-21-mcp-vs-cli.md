# Sidenote: MCP server or CLI?

Date: 2026-08-21

## Short answer

There is a case for an MCP server, but it is narrower than it looks. MCP can replace the command half of the integration (register, ack, lock, reply, anchor, note, turn begin/end). It cannot replace the event half in Claude Code today. The Monitor WebSocket is what wakes the session when a comment arrives; MCP has no equivalent that starts a turn. A switch to MCP therefore gives a split architecture: MCP for commands, Monitor for events. That is more surface, not less.

Recommendation: keep the CLI as the protocol. If you want the MCP ergonomics, add `sidenote mcp` as a second front end over the same `sidenote-core` Store, behind the same binary. Do not remove the CLI. Revisit a full switch if Claude Code gains notification-driven turns from MCP servers, or if you want Sidenote to work with clients other than Claude Code.

## How the integration works today

- `sidenote-core` holds the data model and the turn operations. The CLI is a thin wrapper. Exit codes 0 to 5 are the protocol.
- The skill (`sidenote-review`, embedded in core, installed by the app) teaches the procedure: ack first, `turn begin`, lock before edits, reply, anchor, `turn end`, never resolve.
- Events reach the session through a `Monitor` on `ws://127.0.0.1:47293`. The subprotocol carries `CLAUDE_CODE_SESSION_ID`, so the app routes frames to the owner session.
- Session liveness uses `listeners.json` plus a `pid_alive` check.

## What MCP would improve

1. Typed calls. Each tool has a JSON schema. The model sees parameter names and descriptions without reading skill text. No shell quoting of reply text or of paths with spaces. This is the largest practical win; the quoting failure mode is real for `reply` and `note` text.
2. Structured results. `turn begin` returns an object (threads, diff, lock state) instead of stdout plus an exit code. Error states 2 to 5 become typed error fields. The model cannot confuse exit 4 with exit 5.
3. Session binding for free. Claude Code spawns one stdio MCP server per session. The server knows its session from birth and its death is the session's death. This can replace `listeners.json` and the pid check for the command side. Caveat: verify that the server process inherits `CLAUDE_CODE_SESSION_ID`; if it does not, the app still needs a session handshake.
4. Permission model. MCP tools get per-tool allow rules. Bash calls to `sidenote ...` need a Bash pattern rule instead. You run bypass permissions, so this does not affect you. It affects other users.
5. Portability. An MCP server works in Claude Desktop, Cursor, Codex, and other clients. Today the README says Claude Code only, so this is an option value, not a need.

## What MCP would not improve, or would make worse

1. Wake-up. The product loop is: comment arrives, session acts, reply lands in the card. `Monitor` does the wake-up. MCP servers can send notifications and resource-update events, but Claude Code does not start a turn from them. You would keep the Monitor, the backoff rules, and the polling fallback. Only the command calls move.
2. The hard knowledge stays in the skill. Tool descriptions can hold one-line hints. The multi-step procedure (ack before thinking, lock only when editing, re-anchor after a rewrite, never add `--done` to a reply-only answer) still needs a skill. MCP does not remove the skill; it removes about half of its text.
3. Install surface. The CLI is one symlink. An MCP server needs an entry in the user's Claude Code MCP config (`claude mcp add --scope user`), which the app would write. It is one more thing the welcome sheet manages and one more thing that can drift.
4. Debuggability. A human can run `sidenote threads <doc>` in a terminal and read the answer. `cli/tests/e2e.sh` plays the skill against the CLI. An MCP server needs an inspector or a test client. Both are solvable; both are work.
5. Context cost. MCP tool definitions sit in every session's tool list. Claude Code now defers MCP tools behind ToolSearch, so the cost is small, but the skill-on-demand model is still cheaper for sessions that never review a document.
6. Rewrite cost and a second protocol. A full switch means reimplementing the exit-code protocol as tool results, updating the skill, the e2e test, the app's install path, and the connect prompt. During the transition, two protocols exist.

## Options

| Option | Effort | What you get |
|---|---|---|
| A. Keep CLI, improve ergonomics (`--json` on every command, `reply --file` or stdin for text) | Small | Removes the quoting hazard; no new surface |
| B. Add `sidenote mcp` over the same core, keep CLI and Monitor | Medium | Typed calls and structured results for Claude Code; CLI stays for humans, tests, and fallback |
| C. Replace CLI with MCP | Large | Same as B, minus a human-usable CLI, plus migration risk; wake-up still via Monitor |

Option A is the cheapest fix for the only concrete pain (quoting). Option B is the right shape if you want MCP at all: one core, two front ends, one event path. Option C has no benefit over B.

## Open questions

1. Does a stdio MCP server spawned by Claude Code inherit `CLAUDE_CODE_SESSION_ID`? This decides whether option B can drop `listeners.json`.
2. Do you want Sidenote to work with any client other than Claude Code? If yes, B moves from optional to necessary.
3. Has the quoting hazard actually bitten in practice? If not, option A may be enough.
